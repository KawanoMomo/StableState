線の配線アルゴリズム改善 — Mockup (案A: チャネル方式)

本資料は 「DSLは図形のみ管理、線は自動描画」 の原則を死守したまま、現状の単純ベジェルーティングを Sugiyama 風の 階層+チャネル方式 に置き換える設計案のビジュアル mock です。実装前のレビュー用で、コードはまだ書いていません。

1. 現状の問題 — OTA更新図で観察された3つのパターン

crossing 関係ないブロックを貫通 back-edge ランク逆方向の長距離線 fan-out 同一始点からの分岐

2. 提案: チャネル方式による配線

ランク (=BFS depth) ごとの「列」の上下に固定幅の routing channel を予約します。線は端点 → チャネル → 端点 の3区画 polyline で結ぶことを基本にし、種類ごとに通るチャネルを分けます。
forward ランク順方向 — 直線最短 back-edge bus 図の下端の専用通路で大きく迂回 detour 中段に予約されたチャネルで横切り回避

3. アルゴリズムの骨子 (擬似コード)

入力: 現在の DSL モデル (states + pseudo + transitions、座標とparent付き)
出力: 各 transition の polyline 経路 (端点 → ウェイポイント列 → 端点) 
# Phase 1: ランク分類とエッジ分類
ranks = bfs_rank(states, transitions, seeds=initial_pseudo_targets)  # 既存と同じ
for t in transitions:
    if rank(t.to) > rank(t.from):
        t.kind = FORWARD       # 順方向 — チャネル予約不要、直線可
    elif rank(t.to) < rank(t.from):
        t.kind = BACKWARD      # 逆方向 — back-edge busへ
    else:
        t.kind = LATERAL       # 同ランク — detour channelへ

# Phase 2: チャネル割当
back_bus_y = max_y_of_any_state + GAP
detour_channels = []  # ランク間ごと、上下2本ずつ予約

for t in transitions where t.kind == BACKWARD:
    t.path = [
        port_out(t.from, side='bottom'),
        (port_out.x, back_bus_y),
        (port_in(t.to).x, back_bus_y),
        port_in(t.to, side='bottom'),
    ]

for t in transitions where t.kind == FORWARD:
    if straight_line(t.from, t.to) crosses any unrelated state:
        # 迂回が必要 — 該当 detour channel を予約
        ch = nearest_free_detour_channel(t)
        t.path = [port_out, (port_out.x, ch), (port_in.x, ch), port_in]
    else:
        t.path = bezier(port_out, port_in)  # 既存ベジェ

# Phase 3: 同チャネル内のオフセット (チャネル内で線を縦/横に並べる)
for ch in all_channels:
    for i, t in enumerate(ch.lines):
        t.path.shift_perpendicular(i * SPACING)

# Phase 4: 自己ループ (将来拡張)
for t where t.from == t.to:
    t.path = top_loop(state, side='top')
要点:
  • ベジェは捨てない — 短距離の forward transition は今のベジェのまま。視覚的になめらかな線が消えるのは loss なので使い分ける
  • back-edge bus は1本 — 図の下端に1本だけ予約。垂直オフセットだけで複数の back-edge を共存させる
  • detour channel は需要があるときだけ — 横切り検出 (ss_validate_layout の route_crosses_block) が反応した行のみ予約する
  • DSLは無変更 — 全部レンダリング時の計算。.sstate ファイルは差分純度を保つ

4. スコープ & 非スコープ

項目状態
back-edge を専用バスに逃がす✅ スコープ
横切り検出 → detour channel 予約✅ スコープ
fan-out (choice等) を別チャネル分配✅ スコープ
同方向同ポートの線を縦オフセット分配✅ スコープ (既存の channel_offset 拡張)
composite state 内部の transition✅ スコープ (親座標系で同じアルゴリズム再帰)
自己ループ (a → a)⚠️ 後回し (別Issue化)
note接続⚠️ 後回し (現状の破線維持)
A* 全グリッド探索❌ 非スコープ (前回失敗の経緯あり)
ELK/dagre/graphvizへの外注❌ 非スコープ (DSL差分純度を崩すため)
DSL syntax 拡張 (@route=below 等)⚠️ escape hatch として将来検討

6. レビュー観点

a. back-edge bus 1本でいい? 大規模図でback-edgeが10本超えると bus が混雑する可能性。複数バス (上/下) を許す? → 提案: まず1本で実装、密集したら2本目を自動生成。
b. 「横切り」の判定基準 関連状態 (端点ancestors/descendants) はskip対象。pseudo-stateの取り扱いは? → 提案: choice/fork は端点と等価扱い、initial/final は中継禁止。
c. ベジェ vs polyline の使い分けの基準 短距離直線forward → ベジェ。bus/detour経由 → polyline (直交)。混在UIが醜くないか? → 提案: すべて一貫してorthogonal polylineに寄せる方が視覚的に整いがち。要レビュー。
d. アルゴリズムのテスト容易性 既存 routing.py のユニットテストが activeなので、入出力シグネチャは保ちつつ内部実装を差し替える方針 (TDDで段階的に)。
e. visualization companion この mock は静的SVG。インタラクティブ版 (DSLを貼って即見えるmock) も作る? → 提案: 必要ならSprint 1完了時に docs/specs/channel-routing-playground.html を別途用意。
