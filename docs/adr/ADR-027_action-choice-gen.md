# ADR-027: アクション欄からchoice擬似状態を自動生成

## ステータス

中断（Phase 1リバート済み、再設計要）

## コンテキスト

テーブルのactionセルにif/else構文を記述してchoice擬似状態と分岐遷移を自動生成する機能を開発。Phase 1（フラット分岐）とPhase 2（ネスト分岐）を実装したが、UXの問題が発覚しリバートした。

## 意思決定の記録

### 構文設計

- `if [Guard]` / `elif [Guard]` / `else if [Guard]` / `else` でchoice分岐を記述
- スペース2個インデントで階層を表現（タブは長すぎるため却下）
- `if [`で始まるかどうかでif/else構文かを判定

### DSLが正の原則

- DSLが常に正。テーブルはDSLの表示・編集手段
- 既存のchoice擬似状態がDSLにあれば位置を変更しない
- テーブルからのchoice操作はDSLの追加・変更として反映

### 既存choice検索（方式A）

- 遷移元が同じ状態からの既存choiceを探して再利用する方式を採用
- 方式B（choice IDに命名規則を使う）は不採用。デメリットが見つかれば変更予定

### デフォルト遷移先

- 分岐行で`-> target`を省略した場合、targetドロップダウンの値をデフォルト遷移先として使用
- `/ action`のみの記述も許容

### ネスト対応（Phase 2）

- インデントベースの再帰パーサー
- 各ネストレベルで新しいchoice擬似状態を生成しチェーン
- 自動配置は遷移元状態の右側

## 発覚した問題

### 1. 逆変換と編集の競合

プロパティパネルのtextareaにif/else逆変換テキストを自動入力すると:
- ユーザーがtargetドロップダウンだけ変更しても、textareaのif/elseが検出されてchoiceパスに入る
- 通常遷移への切り替えができない

### 2. 表示モードと編集モードの分離不足

- テーブルセル（表示）とtextarea（編集）で同じif/else逆変換を使った
- 表示はif/else、編集はDSLの生データという分離が必要だった

### 3. target行の表示

- choice IDがそのまま表示され、ユーザーが遷移先を把握できない
- 分岐先を展開表示する修正を入れたが、根本的にはテーブル設計の見直しが必要

## 再設計時の提案

1. **表示と編集の明確な分離**: テーブルセルは逆変換表示（読み取り専用的）、プロパティパネルはDSLベースの編集
2. **モード切替**: if/elseモードと通常モードを明示的に切り替えるUI（トグルボタン等）
3. **choice管理の一元化**: choiceの作成・編集・削除をまとめた専用UI
